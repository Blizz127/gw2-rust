# Build 209026: portal login (cligate STS on TCP 6112)

Runtime captures come from the offline sandbox. Logins used a throwaway test name
(`test@banshee.local`) typed into the launcher with xdotool and sent only to our own
observer. No real credentials were involved. Raw logs are private in `~/re/gw2/notes/`.

## Observed

1. Connect (run 21+), one-way with no `s:`: `P /Sts/Connect STS/1.0` and an XML body:
   `ConnType 400`, `Address`, `ProductType 0`, `ProductName Gw2-64`, `AppIndex 1`,
   `Epoch`, `Program 101`, `Build 1004`, `Process 32`.
2. Idle: `P /Sts/Ping STS/1.0`, `l:0` every 30 s. Not answered, and the client doesn't
   seem to mind.
3. On LOG IN (run 36):
   ```
   P /Auth/StartTls STS/1.0
   s:1;timeout=29000
   l:11

   <Request/>
   ```
   With no reply the client gives up after 29 s, resets and reconnects
   (`P /Sts/Connect` again).
4. We answer `STS/1.0 200 OK`, `s:1R`, `l:8`, `<Reply/>` (run 37). The client
   immediately sends a **TLS 1.2 ClientHello** (56 bytes):
   - record `16 03 03 00 33`, handshake ClientHello, version `03 03`, 32-byte random,
     empty session id;
   - **cipher suites** `002f 0035 003c 003d`: TLS_RSA_WITH_AES_128_CBC_SHA,
     _256_CBC_SHA, _128_CBC_SHA256, _256_CBC_SHA256, all static-RSA key exchange;
   - compression `00` (null), **no extensions**: no SNI, no extended master secret, no
     renegotiation_info.

## Inferred

- The server certificate's RSA key is checked against the pinned cligate keys or the CA
  roots in the trust table at `0x14261ff20` (docs/re/209026-portal-pins.md). Our server
  will present its own RSA key, and the client's pinned `cligate.101` modulus is
  replaced in memory only.
- After the handshake, the account login (name/password, or a token) travels inside TLS
  as STS messages. The 2012–13 notes describe `/Auth/LoginStart` and an SRP exchange.
  The suites offered here don't include SRP.
