**Field kinds** use the same mapping as `mission.xml`, plus:
- kind 9 = Float4, verified in [primitive fields](209026-primitive-fields.md);
- kind 10 = Point3, verified in [agent creation](209026-agent-creation.md).

Kind 15 is **Optional**. It appears in clients 4, 7, 9, 10 and 11, often nested. The
client's field codec dispatches by kind:
- the encoder through the table at `0x140ff178c + 4·kind`, bounded by `cmp eax,0x1a`;
- the receiver through `0x140ff237c + 4·(kind−1)`, bounded by `cmp eax,0x19`;
- kind 9 lands on the documented `0x140ff096a` and `0x140ff1da3`, which confirms the
  indexing.

Kind 15's handlers:
- **Encoder `0x140ff0d81`:** reads the 8-byte field pointer and writes `setne`, one byte
  that is 0 or 1. When the pointer is non-null, it encodes the nested descriptor at field
  +0x18.
- **Receiver `0x140ff1eeb`:** bounds-checks and reads one byte. Zero stores null. Nonzero
  allocates the nested struct size (field +0x20) and recurses into the message decoder
  `0x140ff1c60` with the nested descriptor.
- **Metadata** `0x1421108c0 + 8·15 = (8, 0)` is the host pointer size, not wire bytes.

So the wire form is one presence byte, then the nested fields only when present. That's
the existing dynamic `Optional` codec with a nested Struct. Our decoder accepts only 0 and
1, which is all the client's encoder writes. Evidence:
`ev_092b54b5af72027586fb37913bac5d9d0e612129d8c21aa53e03a2135b78ec0d` (dispatch and both
handlers); the regenerated schema is
`ev_5b538d658734c4a08004f5f9295b7c95e9688e74367551a0db9eef90ed810aa6`. Private bundle:
