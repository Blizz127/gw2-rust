# Build 209026: group-0 (agent) client messages

Static REA result for the frozen client (`Gw2-64.exe`, sha256 `99342078…8621`).

**The table.**
- 23 descriptor pointers at **`0x14211bdb0`**, null-terminated at `0x14211be68`.
- It sits right after the source path `…\Engine\Agent\AgMsg.cpp`.
- The (descriptor, handler) server table of the same file follows at `0x14211be70`
  (ids 31 and up).
- Client ids: **3–11, 13–26**. Id 12 is absent here and is a group-39 mission client
  message. None of these ids collides with the group 39/40 client ids.
- Client 17's descriptor `0x1425b7260` is the one Word delay report from
  [command clock](209026-agent-command-clock.md).

**Field kinds** use the same mapping as `mission.xml`, plus:
- kind 9 = Float4, verified in [primitive fields](209026-primitive-fields.md);
- kind 10 = Point3, verified in [agent creation](209026-agent-creation.md).

Kind 15 is **Optional**. It appears in clients 4, 7, 9, 10 and 11, often nested. The
client's field codec dispatches by kind:
- the encoder through the table at `0x140ff178c + 4·kind`, bounded by `cmp eax,0x1a`;
- the receiver through `0x140ff237c + 4·(kind−1)`, bounded by `cmp eax,0x19`;
- kind 9 lands on the documented `0x140ff096a` and `0x140ff1da3`, which confirms the
  indexing.

Kind 15's handlers:
- **Encoder `0x140ff0d81`:** reads the 8-byte field pointer and writes `setne`, one byte
  that is 0 or 1. When the pointer is non-null, it encodes the nested descriptor at field
  +0x18.
- **Receiver `0x140ff1eeb`:** bounds-checks and reads one byte. Zero stores null. Nonzero
  allocates the nested struct size (field +0x20) and recurses into the message decoder
  `0x140ff1c60` with the nested descriptor.
- **Metadata** `0x1421108c0 + 8·15 = (8, 0)` is the host pointer size, not wire bytes.

So the wire form is one presence byte, then the nested fields only when present. That's
the existing dynamic `Optional` codec with a nested Struct. Our decoder accepts only 0 and
1, which is all the client's encoder writes. Evidence:
`ev_092b54b5af72027586fb37913bac5d9d0e612129d8c21aa53e03a2135b78ec0d` (dispatch and both
handlers); the regenerated schema is
`ev_5b538d658734c4a08004f5f9295b7c95e9688e74367551a0db9eef90ed810aa6`. Private bundle:
`~/re/gw2/notes/209026-agent-client-2.json`.

## Server registration tables and the emitted-frame audit

`~/re/gw2/notes/extract-server-tables.py` scans the image's .rdata and .data for runs of
(descriptor, handler) pairs, where the descriptor starts with a message-id field and the
handler points into .text.
- It finds **50 tables, 1253 server messages**. No field kind is unknown any more.
- It writes them to `data/protocol/209026/server-tables.xml` (local, gitignored), one
  group per table (225649 bytes).
  - Regeneration evidence: `ev_49f5dea5f12197fb072acfa7eca78b9f8ee235bf9b92450badd0b5cbe0c383f4`.
  - Exact sha256: `f64a99ebb7397a49b5df65736d5678ecee1f21dc210a0a6561062dbb437de8ae`.
  - Private bundle: `~/re/gw2/notes/209026-server-tables-1.json`.

**Kind 26 frames as Qword** (8 raw bytes).
- It's used in one message, server 782 (table `0x1422413e8`), inside an array.
- Its receiver `0x140ff22fe` is kind 5's own: it copies 8 raw bytes and advances 8.
- Its metadata `(8, 1)` equals kind 5's, meaning 8 bytes, fixed width.
- Its encoder `0x140ff1432` writes one raw 8-byte value per field, with no varint step.
- Kind 5's encoder is a different routine (`0x140ff06ae`), so the two kinds may differ in
  meaning, for example a time or handle type. Only the framing is equal.
- Evidence: `ev_1e20a6c688f36e339aa4e128264feb1f62af3261457b6d5743f3af798a0cbee0`
  (`kind26-windows.py`).

The game connection's group-0 server messages are split across tables:
- the 624-entry table `0x14216e940`;
- AgMsg.cpp's `0x14211be70` (ids 31–88, e.g. 37 agent creation and 46 world entry);
- mission groups 39 (`0x1422ddbf0`) and 40 (`0x141923b80`).

Ids are not unique across all tables. Server 444 is also registered in `0x1422e03b0`
(ids 444–1139) with another layout, apparently a different protocol.

The test `every_emitted_server_frame_matches_a_client_handler_descriptor` decodes every
frame the deployed mission phase sends against those game tables, in that order. It
requires a registered handler and exact length. All 20 frames pass:
- opening: 1063, 1060;
- population: 428, 37, 443, 183, 282, 477, 151, 247, 248, 565, 538, 605, 170, 618, 444, 46;
- begin: 1036, 431.

So on the client side none of them can hit DISCONNECT_MISSING_HANDLER or BAD_COUNT through
framing. Handler-level dispatch failures (value checks) are not covered by this audit.
